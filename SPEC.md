# SPEC — smart-lab

**Spec version:** `s0.5.3` (see "Spec versioning" below for what this means)
Living design spec, updated collaboratively across the Cowork design session and Claude Code builds.
Last updated: 2026-09-17.

## Purpose
Help manage lab work: tracking cases and their samples through a workflow, logging measurements and actions, giving clients visibility into progress, collecting client reviews after closure, and producing a report section (docx) that gets inserted into the official report authored elsewhere.

Built for real day-to-day lab work (real-use mode, not a learning project). Terminology note: the top-level unit of work is called a **Case** (not "job").

## Spec versioning
This document has its own version, separate from the app's version (see the app's "Versioning" section below) — format `sJ.M.P`, the leading `s` marking it as the *spec's* version so it's never confused with the app's own `MAJOR.MINOR.PATCH`.
- **J** (major) — bumped for a major overhaul of the design itself (e.g. a fundamental restructuring, not just new detail).
- **M** (minor) — bumped when a new feature area gets finalized through discussion (goes from open/undecided to settled).
- **P** — bumped for each discussion-driven edit to this document that isn't a J or M bump (i.e. the default increment for routine updates).
- Baseline `s0.1.0` set 2026-09-17, reflecting everything settled up to that point without retroactively reconstructing a precise edit-by-edit history; counting forward starts from here.

## Environment
- **Open network** (regular internet, reachable from phone) — this is where this app lives. It tracks in-progress cases, their workflow/status, gives clients visibility, and offers some utilities (TBD).
- **Closed network** (separate, no internet) — used for writing the final official report and long-term documentation/archival. Out of scope for this app; no integration attempted. This app produces a docx section formatted so it can be inserted into that closed-network report, since there's an existing way to bring docx content in.
- **Dev workflow**: built on the open network using Claude Code, pushed to GitHub, deployed via GitHub Pages + Firebase (per App Build Standards). Not affected by the closed-network constraint since this app never needs to run there.
- **Core scoping principle**: this app tracks *cases in progress*. It is explicitly not a long-term archive — see "Archiving" below.

## Roles
- **Team leader** — currently the only role that can open a new case. Assigns a case manager to the case (any `worker` or `team_leader` account, including themselves), sets up samples/zones/lab workflows and the archiving workflow, drives the case's stage transitions ("start lab," "publish report," "approve & delete"), sets the `onHold`/`highPriority`/`showResearchToClient` toggles, and is the only one who can perform final deletion at `done`.
- **Case manager** — a specific person (`worker` or `team_leader`) named on a case, not a distinct stored role. Runs the case day-to-day; can also mark `researchAddressed`.
- **Operator (worker)** — executes actions. Every action (this iteration, always a free-form action) gets a name, optional zone, free-text notes/results, and who/when executed it — no separate "measurement value" shape, no verifier sign-off (see below).
- **Verifier** — a role certain people hold (not assigned per-action by name). Some actions require sign-off from any verifier in addition to the operator's execution.
- **Client** — participates in the initiation meeting (with case manager + team leader) that precedes a case being opened. While the case is in progress, sees status only (stage name, per sample — see "Client-facing view"). After closure, gets a review request. Represents whoever attends from the client's side (could be multiple people; treated as one entity for now).
- **Admin** — confirmed role. Can add users, delete users, change a user's status (e.g. active/disabled), and change a user's password. May also get elevated access for review anonymity — still deferred. **Exclusive, single-account role (settled 2026-09-17, built and confirmed):** exactly one admin account exists, ever. It's never offered as an assignable role for any other user, and it can't hold any other role or the verifier tag — the admin account is scoped purely to configuration/user-management (adding users, editing roles/status, reissuing passwords), not a workflow participant. Confirmed no rules-level gap exists for self-promotion: `users/{uid}` writes require the caller to already be admin, with no self-write exception, so this is enforced by the rules, not just the admin screen hiding an option.
- *(Dev — you, building the app. Not a workflow participant, not necessarily an in-app role.)*

**Build-time simplification (for now, 2026-09-17):** the actual stored `role` field on a user account only distinguishes four values — `client`, `team_leader`, `worker` (an umbrella covering both Case manager and Operator, collapsed together until the real workflow model in Phase plan item 4 needs to split them back out), and `admin`.

**Verifier — removed for now, redesign pending (2026-09-17):** originally a boolean tag combinable with `team_leader`/`worker`, it was built in Iteration 3 and then stripped back out entirely (UI, data model, admin screen) during testing — it'll come back later in a different shape, not yet designed. Not applicable to `client` or `admin` either way.

**Admin exclusivity, mechanics (settled and built 2026-09-17):** the admin screen's role selector — both the add-user form and the inline per-user role editor — never lists `admin` as an option, only `client` / `team_leader` / `worker`. The admin's own row in the user list is shown read-only (no role/status edit controls), since there's nothing to edit and no second admin to promote. The single admin account is seeded manually, once (see "Bootstrapping the first admin" below), and stays admin permanently; there's no in-app path to create a second one or to promote/demote into or out of it.

## Authentication
- All in-app accounts (team leader, case manager, operator, verifier) use **synthetic/fake emails** under the hood (e.g. `username@smart-lab.internal`) paired with a password — the login UI just asks for username + password. No real personal emails are stored for anyone, including the app owner's own account, to avoid exposing real addresses.
- Because fake emails can't receive real reset links, there's no self-service "forgot password" flow — and **correction (2026-09-17)** to an earlier assumption here: the Firebase Console can't fill that gap either. Its only password action is "send a password-reset email," which nothing will ever receive at a fake `@smart-lab.internal` address. Deleting another user's Auth account, or changing their password without them doing it themselves, both genuinely require the Firebase Admin SDK — in practice a Cloud Function behind an Admin UI — which needs Firebase's Blaze (pay-as-you-go) plan (usage at this scale should stay within its free tier, but a card on file is required to enable it at all).
- **Decision (2026-09-17): stay on Spark, no Blaze.** Rather than build custom auth from scratch (considered and rejected — it would drop Firestore security rules' only real enforcement mechanism, since rules trust `request.auth`, which only exists via a real auth provider like Firebase Auth), the answer is to keep using Firebase Auth but design around ever needing to act on *another* user's account via the Admin SDK.

### User identity model (settled 2026-09-17)
The stored `username` is the stable, permanent identity — it's what any future case/action assignment should reference, **never** the underlying Firebase Auth `uid`, because the `uid` behind a username can change (see Reissue below). Two Firestore pieces:
- **`users/{uid}`** — one per Firebase Auth account: `username`, `role`, `verifier`, `status` (`active`/`disabled`). A disabled account is never deleted; it just sits permanently inert, at no cost.
- **`usernames/{username}`** — one per login username: `authEmail`, the synthetic email currently valid for signing in as that username. Public read (needed to resolve a typed username before sign-in is even possible), admin-only write. This indirection is what makes a reissue possible without disturbing the username itself.
- **Login flow**: username → read `usernames/{username}` for `authEmail` → `signInWithEmailAndPassword(authEmail, password)` → on success, read `users/{uid}` for role/verifier/status.
- **Add a user** (admin, no Blaze needed): a second, throwaway Firebase app instance creates the new Auth account without disturbing the admin's own session; then `users/{newUid}` and `usernames/{username}` get written from the primary (admin) session.
- **Reissue** — this is how "change a user's password" actually works, replacing a true Admin-SDK reset: admin creates a *new* Firebase Auth account (a fresh internal email, since the old one can't be reused without deleting the old account — no Admin SDK needed to create it, same trick as above), copies `username`/`role`/`verifier` onto a new `users/{newUid}` doc, disables the old `users/{oldUid}`, and repoints `usernames/{username}.authEmail` at the new account. The person keeps logging in with the exact same username; only the password (and an internal email they never see) changed. Anything ever assigned to them by username is completely undisturbed, since it never referenced the `uid`.
- **Delete may never actually be needed**: disable (free, permanent) covers "this person shouldn't have access," and reissue covers "this person needs a new password" — between the two, there may be no real remaining use for a true Auth-account delete. If one ever comes up, the Firebase Console can do it directly at no cost (a real no-cost fallback, unlike password changes) — not planned as an in-app feature.
- **Bootstrapping the first admin**: since role-editing is admin-gated, the very first admin account can't grant itself that role through the app (no admin exists yet to do the granting). It's seeded once, manually: both `users/{uid}` (`role: "admin"`) and `usernames/{username}` (`authEmail`) written directly in the Firebase Console's Firestore data browser — a one-time setup step, not an ongoing capability. Per the Roles section's admin-exclusivity rule, this manual bootstrap is expected to be the *only* time an admin account is ever created — the app itself never offers a way to make a second one.

## Case lifecycle (redesigned 2026-09-17, see Decisions Log)
A case's `stage` field is a **fixed, built-in state machine** — five stored values (`new` covers what was originally discussed as two separate stages, "new" and "planning" — both are just "the case is being set up," and the client shows the identical "In lab" label for either one, so there's no reason to store them separately). Unlike the archiving/lab workflows (freely authored by the team leader), this sequence itself is not user-customizable.

1. **`new`** — case created (client + case manager + team leader have already had the initiation meeting, outside the app), starting from just a `caseNumber`. Case-level fields, samples, zones, each sample's lab workflow, and the archiving workflow all get set up here. **Client-visible from this point on** (not hidden pre-lab) — see "Client-facing view" below.
2. **`lab`** — entered via an explicit "Start lab" action (team leader/admin). Samples' actions get executed. Client-visible, with the same **"In lab"** label as `new`.
3. **`writing`** — entered **automatically** once every sample has every one of its actions marked done (no explicit button). The official report is authored outside this app (closed network). Client-visible as **"Writing."**
4. **`archiving`** — entered via an explicit "Publish report" action (team leader), **blocked unless `researchAddressed` is true** (see "Research" below). This is also the moment the case drops out of client visibility entirely (informally "closed" from the client's perspective, but not a stage of its own) and — once Reviews exist — the review request would fire here. The archiving workflow's actions (see "Case / Sample / Action model") get executed. Not client-visible.
5. **`done`** — entered via an explicit "Approve & delete" action, **team leader only**. **The case is completely deleted from the app** at this point — this is real deletion, not a soft archive, since the app's job is only to track cases in progress and the authoritative long-term record lives in the closed-network report. If a review was submitted, it is retained independently of the case record (so it survives the case's deletion).

**Research** runs alongside both `lab` and `writing` without blocking either — it's tracked as a single case-level `researchAddressed` flag (not per sample), manually set by the team leader or case manager once research is sufficiently wrapped up. Its own internal shape (checklist / workflow / freeform notes) is still an open question, but whatever form it takes, `researchAddressed` is the one signal that gates the `writing` → `archiving` transition — nothing about research itself blocks `lab` or `writing`.

**On hold** and **high priority** are two independent, team-leader-only boolean flags on a case, orthogonal to `stage` — pure display badges (visible to the client and internally to the case manager), no enforced behavior on top of them.

## Case / Sample / Action model (redesigned 2026-09-17, see Decisions Log)
- **Identifiers**: cases and samples both use opaque, hidden internal IDs — never a human-entered value as the actual database key, so renaming/correcting a name or number is always a cheap field edit, never a data migration.
- **Case-level fields**: `caseNumber` (mandatory — a real number in `YYMMNXX` format, or an auto-generated `tempN` placeholder until the real one's known; editable later, no migration cost), `clientCaseNumber` (optional, same format, a reference to a distinct case tracked on the client's own side), `name` (the case's own short title), `clientName`, `caseManager` (a `worker` or `team_leader` username — a team leader can manage their own case), `startDate`, `expectedTimelineDate`, `stage` (see "Case lifecycle"), `onHold`/`highPriority`/`showResearchToClient` (team-leader toggles), `researchAddressed` (gates archiving), and `archivingWorkflow`.
  - `caseNumber`/`clientCaseNumber` format: `YY` (year) + `MM` (month) + one department digit (`5` = this lab's own cases; `4` = the one known client so far, more values presumably later) + a 2-or-3-digit running number (`XXX` rare — never a single digit). Soft-validated (shape + month range) with a dismissible warning on mismatch; never blocks saving.
- **Sample fields**: `name` (required, unique within the case), `groupName` (optional, for samples from the same composite part — display/reference identifier is `groupName - name`, no effect on tracking), `zones` (optional list of zone names).
- **Action** (one type only this iteration — a **free-form action**, repeatable as many times as needed): `name`, an optional `zone` (one of the sample's zones, or none for whole-sample), `notes` and `results` (both free text), `executedBy`/`executedAt` (set on completion). No `assignedTo` (actions go straight from unclaimed to executed) and no verifier fields (out of scope this iteration — see Roles). Covering the same test across several zones means adding the action again per zone, not one instance holding multiple zones' results.
- **Lab workflow** (per sample) = that sample's list of actions. Every new sample is seeded with a **fixed default**: Visual Inspection, then Composition Analysis and Hardness Test in parallel (hardcoded this iteration, not a per-case configurable catalog). Further free-form actions can be added to a sample at any time beyond the three defaults.
- **Archiving workflow** (per case) = a small array field directly on the case document (not a subcollection — always edited as a whole), seeded when the case is set up: Publish → Close-in-access → (Return parts ‖ Archive samples) → Scan. Freely editable afterward by the team leader (rename, remove, or add items) like any other set of free-form actions — e.g. renaming "Return parts" to "Salvaging" for a case where that's what actually happens, or dropping a step that doesn't apply. No separate "alternate action" mechanism — this is just ordinary editing of the seeded default.
- **Ordering within a workflow** (lab or archiving): steps run as a sequence of one-or-several-parallel items — an item can't start until everything before it in the sequence is done, but items sharing a slot (like Composition Analysis/Hardness Test, or Return parts/Archive samples) have no order between themselves. This ordering is **informational/display-only for this iteration** — nothing is actually blocked from being marked done out of order; real enforcement is a later refinement if it turns out to matter.
- A workflow is a generic, recursive primitive (a workflow contains actions; an action can itself be a nested workflow) — this iteration only exercises one level of that (a flat list of free-form actions, some grouped in parallel), not actual nesting.

## Client-facing view (current scope; not yet built — see Phase plan item 5)
- **Single shared public link, no login and no per-client ID/code at all.** Anyone with the link can view it — security is intentionally lightweight here per the owner's preference.
- **Case visibility (revised 2026-09-17)**: a case is visible to the client from the moment it's created (`stage == "new"`), not hidden during setup. Status shown is case-level (not per-sample anymore): **"In lab"** (covers both `new` and `lab` — no distinction shown between them) → **"Writing"** → invisible again once the case reaches `archiving` (report published). If the case's `showResearchToClient` is on and `researchAddressed` isn't true yet, an extra "research ongoing" note is appended to whichever status is showing. `onHold` and `highPriority` are also both shown to the client as badges when set.
- **Default view**: lists every visible case's status as above, filterable by client name (a field stored on each case).
- **Lean view** (toggle, off by default): a condensed per-case listing showing status, start date, day count (days elapsed since start, derived), and expected timeline date. Aimed mainly at a client-side "team leader" contact who wants a quick overview, but reachable by anyone via the toggle — no separate access tier enforced.
- **Shadow cases toggle** (nested inside lean view only, off by default): reveals shadow cases (see below) alongside real cases. Also not access-gated — just an extra step to find.

## Shadow cases
- Represents a case that's expected to start soon but hasn't formally opened yet — a heads-up placeholder, not a full case.
- No case number. May carry an internal-only identifier not shown to any user.
- Holds mostly free notes; rarely needs more structure than that.
- Visible to the lab's team leader, and to clients only via the lean-view shadow toggle (see above).
- Later "evolves into" a real case once it's ready to formally open — exact mechanics (same record promoted into a Case vs. a new Case created separately and the shadow entry cleared) still open, see Open Questions.

## Versioning
- Format: **MAJOR.MINOR.PATCH**, starting at `0.1.0`.
- **Patch** bumps for a fix to something already launched (e.g. `0.2.0` → `0.2.1`).
- **Minor** bumps once a feature is considered done and launched for real use; patch resets to 0 (e.g. `0.1.3` → `0.2.0`).
- **Major** has no concrete trigger yet beyond the semver default: `1.0.0` marks the app going into real day-to-day use for actual cases (replacing whatever's used today); later majors would mark something similarly big (a major re-architecture, a new module) — to be decided when it comes up.
- **Testing suffix, `docs/test/`-only (revised 2026-09-17)**: while a version is still being proven out on `docs/test/`, it carries a `-tNN` suffix (two digits, zero-padded), e.g. `0.3.0-t01`, `0.3.0-t02`, `0.3.0-t03`... Once satisfied, it's promoted to `docs/` (root) as the plain version with the suffix dropped (`0.3.0`). **`docs/` itself never carries a `-tNN` suffix, even for a change made directly on root** (e.g. a small fix that doesn't go through a `docs/test/` pass first) — it's committed straight as a plain patch or minor bump instead. Originally (iterations 1–2, before `docs/test/` existed as a permanent fixture) root did cycle through its own `-tNN` passes; now that `docs/test/` is the standing place where work gets proven out first, root doesn't need a second testing cycle on top of that. The base number (minor vs. patch) says *what kind* of change it is; the `-tNN` suffix (on `docs/test/` only) says *whether it's been proven out yet*.
- Displayed at the **top** of the app (e.g. near the header/app name), not in a footer — makes it easy to confirm which build loaded during active testing.
- Doubles as the mechanism for the "update available, refresh?" pattern from the App Build Standards: the running app's version is compared against the deployed version, and a mismatch triggers the prompt rather than a silent reload. **Implemented in `0.1.0-t02`+**: polls its own `index.html` on load and on tab-visibility-regained, regex-matches the `APP_VERSION` constant, shows a dismissible banner with a Reload button on mismatch (no interval polling — see Decisions Log).

## Environments (testing vs. launched)
The owner wants to keep working on a testing build while colleagues/clients continue seeing the last launched version, rather than everyone seeing every in-progress change immediately.
- **Two live URLs from the same repo, no branches or build step needed**: the launched app lives at `docs/` (the repo's GitHub Pages source folder, effectively the site root — see `CLAUDE.md`'s "Repo layout"; what colleagues/clients use); the working/testing build lives in a `docs/test/` subfolder, served by the same GitHub Pages deployment. "Launching" a tested version means copying `docs/test/`'s files up to `docs/` and dropping the `-tNN` suffix from the version string.
- **Data separation, same Firebase project**: originally planned as Firestore's **multiple databases** feature (a second named database, e.g. `test`, alongside `(default)`) rather than a naming convention, to avoid the risk of a missed prefix silently writing test data into production. **Revised 2026-09-17**: that feature needs the paid Blaze plan; on Spark (free, what this project is on) only `(default)` exists. Interim approach is a collection-name prefix instead — `docs/`'s round-trip test writes `ping`, `docs/test/`'s writes `test_ping` — accepting the original risk for now. Auth stays shared across both either way (only the data separation approach changed). Revisit real database-level isolation if the project ever moves to Blaze.
  - Build notes (superseded by the 2026-09-17 revision above, kept for if/when this project moves to Blaze): a named database would be created via the `gcloud` CLI (`gcloud firestore databases create --database=test --location=... --type=firestore-native`) or possibly the Firebase Console directly. Security Rules are deployed **per database**, so both databases would need their rules deployed separately. The Web SDK connects to a specific database via `getFirestore(app, "test")` instead of the plain `getFirestore(app)` for default.
- **Not separately installable**: `docs/test/` has no manifest/service-worker of its own — Android can't offer two independent home-screen install icons when one URL path is nested under the other (manifest `scope` is a strict prefix match with no way to exclude a subpath; confirmed after trying an explicit `id` field and a clean uninstall/reinstall, still collided). `/test/` is accessed via browser bookmark/tab instead. The real fix would be a second repo at a sibling (non-nested) path, not attempted since it costs a second repo to keep in sync — revisit only if separate installability starts to matter.
- **Status**: built in iteration 2, both pieces user-verified (root launched at `0.1.0`; `docs/test/`'s writes confirmed landing in `test_ping`, distinct from root's `ping`).

## Report

## Reviews
- Triggered when the report is published (the `writing` → `archiving` transition — see "Case lifecycle"; this was previously described as "when a case reaches closed," before that stage name was retired).
- Client can: decline (removes the request entirely), review later (dismisses the prompt but keeps the link available), or complete it.
- A completed review has several 1-5 ranking questions plus a free-text area (exact question set TBD).
- Reviews are stored independently of the case record, so they survive the case's eventual deletion at `done`.
- Admin may need elevated access here for anonymity reasons — deferred.
