# SPEC — smart-lab

**Spec version:** `s0.3.0` (see "Spec versioning" below for what this means)
Living design spec, updated collaboratively across the Cowork design session and Claude Code builds.
Last updated: 2026-09-17.

## Purpose
Help manage lab work: tracking cases and their samples through a workflow, logging measurements and actions, giving clients visibility into progress, collecting client reviews after closure, and producing a report section (docx) that gets inserted into the official report authored elsewhere.

Built for real day-to-day lab work (real-use mode, not a learning project). Terminology note: the top-level unit of work is called a **Case** (not "job").

## Spec versioning
This document has its own version, separate from the app's version (see the app's "Versioning" section below) — format `sJ.M.P`, the leading `s` marking it as the *spec's* version so it's never confused with the app's own `MAJOR.MINOR.PATCH`.
- **J** (major) — bumped for a major overhaul of the design itself (e.g. a fundamental restructuring, not just new detail).
- **M** (minor) — bumped when a new feature area gets finalized through discussion (goes from open/undecided to settled).
- **P** — bumped for each discussion-driven edit to this document that isn't a J or M bump (i.e. the default increment for routine updates).
- Baseline `s0.1.0` set 2026-09-17, reflecting everything settled up to that point without retroactively reconstructing a precise edit-by-edit history; counting forward starts from here.

## Environment
- **Open network** (regular internet, reachable from phone) — this is where this app lives. It tracks in-progress cases, their workflow/status, gives clients visibility, and offers some utilities (TBD).
- **Closed network** (separate, no internet) — used for writing the final official report and long-term documentation/archival. Out of scope for this app; no integration attempted. This app produces a docx section formatted so it can be inserted into that closed-network report, since there's an existing way to bring docx content in.
- **Dev workflow**: built on the open network using Claude Code, pushed to GitHub, deployed via GitHub Pages + Firebase (per App Build Standards). Not affected by the closed-network constraint since this app never needs to run there.
- **Core scoping principle**: this app tracks *cases in progress*. It is explicitly not a long-term archive — see "Archiving" below.

## Roles
- **Team leader** — currently the only role that can open a new case. Assigns a case manager to the case, defines the case's workflow (from a maintained catalog/skeleton of actions, plus custom actions), defines the archiving workflow (steps to run after the report is published), and signs off final archiving (which deletes the case).
- **Case manager** — assigned to a case by the team leader. Runs the workflow day-to-day: assigns individual actions to operators.
- **Operator** — executes actions. Every action gets at minimum a date + operator name; actions that need more (e.g. measurements) get the actual recorded values, stored in this app.
- **Verifier** — a role certain people hold (not assigned per-action by name). Some actions require sign-off from any verifier in addition to the operator's execution.
- **Client** — participates in the initiation meeting (with case manager + team leader) that precedes a case being opened. While the case is in progress, sees status only (stage name, per sample — see "Client-facing view"). After closure, gets a review request. Represents whoever attends from the client's side (could be multiple people; treated as one entity for now).
- **Admin** — confirmed role. Can add users, delete users, change a user's status (e.g. active/disabled), and change a user's password. May also get elevated access for review anonymity — still deferred.
- *(Dev — you, building the app. Not a workflow participant, not necessarily an in-app role.)*

**Build-time simplification (for now, 2026-09-17):** the actual stored `role` field on a user account only distinguishes four values — `client`, `team_leader`, `worker` (an umbrella covering both Case manager and Operator, collapsed together until the real workflow model in Phase plan item 4 needs to split them back out), and `admin`. **Verifier isn't one of these four** — it's a separate boolean tag, combinable with `team_leader` or `worker` (not applicable to `client`), since holding it doesn't change which of the four base roles someone otherwise has.

## Authentication
- All in-app accounts (team leader, case manager, operator, verifier) use **synthetic/fake emails** under the hood (e.g. `username@smart-lab.internal`) paired with a password — the login UI just asks for username + password. No real personal emails are stored for anyone, including the app owner's own account, to avoid exposing real addresses.
- Because fake emails can't receive real reset links, there's no self-service "forgot password" flow — and **correction (2026-09-17)** to an earlier assumption here: the Firebase Console can't fill that gap either. Its only password action is "send a password-reset email," which nothing will ever receive at a fake `@smart-lab.internal` address. Deleting another user's Auth account, or changing their password without them doing it themselves, both genuinely require the Firebase Admin SDK — in practice a Cloud Function behind an Admin UI — which needs Firebase's Blaze (pay-as-you-go) plan (usage at this scale should stay within its free tier, but a card on file is required to enable it at all).
- **Decision (2026-09-17): stay on Spark, no Blaze.** Rather than build custom auth from scratch (considered and rejected — it would drop Firestore security rules' only real enforcement mechanism, since rules trust `request.auth`, which only exists via a real auth provider like Firebase Auth), the answer is to keep using Firebase Auth but design around ever needing to act on *another* user's account via the Admin SDK.

### User identity model (settled 2026-09-17)
The stored `username` is the stable, permanent identity — it's what any future case/action assignment should reference, **never** the underlying Firebase Auth `uid`, because the `uid` behind a username can change (see Reissue below). Two Firestore pieces:
- **`users/{uid}`** — one per Firebase Auth account: `username`, `role`, `verifier`, `status` (`active`/`disabled`). A disabled account is never deleted; it just sits permanently inert, at no cost.
- **`usernames/{username}`** — one per login username: `authEmail`, the synthetic email currently valid for signing in as that username. Public read (needed to resolve a typed username before sign-in is even possible), admin-only write. This indirection is what makes a reissue possible without disturbing the username itself.
- **Login flow**: username → read `usernames/{username}` for `authEmail` → `signInWithEmailAndPassword(authEmail, password)` → on success, read `users/{uid}` for role/verifier/status.
- **Add a user** (admin, no Blaze needed): a second, throwaway Firebase app instance creates the new Auth account without disturbing the admin's own session; then `users/{newUid}` and `usernames/{username}` get written from the primary (admin) session.
- **Reissue** — this is how "change a user's password" actually works, replacing a true Admin-SDK reset: admin creates a *new* Firebase Auth account (a fresh internal email, since the old one can't be reused without deleting the old account — no Admin SDK needed to create it, same trick as above), copies `username`/`role`/`verifier` onto a new `users/{newUid}` doc, disables the old `users/{oldUid}`, and repoints `usernames/{username}.authEmail` at the new account. The person keeps logging in with the exact same username; only the password (and an internal email they never see) changed. Anything ever assigned to them by username is completely undisturbed, since it never referenced the `uid`.
- **Delete may never actually be needed**: disable (free, permanent) covers "this person shouldn't have access," and reissue covers "this person needs a new password" — between the two, there may be no real remaining use for a true Auth-account delete. If one ever comes up, the Firebase Console can do it directly at no cost (a real no-cost fallback, unlike password changes) — not planned as an in-app feature.
- **Bootstrapping the first admin**: since role-editing is admin-gated, the very first admin account can't grant itself that role through the app (no admin exists yet to do the granting). It's seeded once, manually: both `users/{uid}` (`role: "admin"`) and `usernames/{username}` (`authEmail`) written directly in the Firebase Console's Firestore data browser — a one-time setup step, not an ongoing capability.

## Case lifecycle
1. **Initiation meeting** — client + case manager + team leader discuss the case.
2. **Case opened** (stage: `new`) — team leader opens the case, assigns a case manager, defines the workflow (actions needed, drawn from a catalog/skeleton with room for custom additions) and the archiving workflow (post-report steps). Workflow is mostly shared across all samples in the case, but the team leader can add extra actions scoped to a specific sample.
3. **Workflow execution** (stage: `in lab`, tracked **per sample**) — case manager assigns actions to operators. Sub-stages per sample, in typical order: sample preparation → pre-etch → post-etch. Some actions require a verifier's sign-off in addition to the operator's.
4. **Research** (stage: `research`, tracked **per sample**) — happens once a sample's lab work is done. Shape not yet decided (could be checklist, workflow, or notes).
5. **In writing** (case-level, once all samples have finished lab + research) — the official report is authored (on the closed network); this app exports a docx section to be inserted into it.
6. **Closed** (case-level) — report has been published to the client. Client receives a review request (ranking questions 1-5 plus a free-text area — exact questions TBD). Client can decline (removes the request) or choose to review later (closes the prompt without removing the link, so they can still complete it). Aside from the review prompt, the case becomes invisible to the client from this point on.
7. **Ready to archive** (case-level) — the archiving workflow (defined back in step 2) is executed.
8. **Archived** (case-level) — team leader signs off. **The case is completely deleted from the app** — this is real deletion, not a soft archive, since the app's job is only to track cases in progress and the authoritative long-term record lives in the closed-network report. If a review was submitted, it is retained independently of the case record (so it survives the case's deletion).

Note: this is the *typical* path and order — real cases can deviate as they evolve, so the stage model shouldn't be a rigid fixed state machine.

## Case / Sample / Action model
- A case can have multiple samples. Some stages are tracked **per sample** (`in lab` and its sub-stages, `research`); others are **case-level milestones** that apply once all samples have finished their individual work (`new`, `in writing`, `closed`, `ready to archive`, `archived`).
- **Workflow** = the set of actions needed for a case. Drawn from a maintained catalog/skeleton, with support for fully custom actions. Applied by default to every sample in the case; the team leader can add sample-specific extra actions on top.
- **Archiving workflow** = a separate action list, defined by the team leader when the case is opened, executed after the report is published (step 7 above).
- **Action** — minimally requires date + operator name once done. Some actions require additional documentation (e.g. measurement values), which **are stored in this app** (this supersedes an earlier assumption that only lighter/status-level data would live here — actual values are in scope). Some actions additionally require a verifier's sign-off.
- Known Case-level fields so far: client name, start date (when the case is opened / enters `new`), expected timeline date (a target/estimated completion date, set by the team leader alongside the workflow at case-open). Full field list still TBD (see Open Questions).

## Client-facing view (current scope)
- **Single shared public link, no login and no per-client ID/code at all.** Anyone with the link can view it — security is intentionally lightweight here per the owner's preference.
- **Default view**: lists every currently open case's status — stage name, per sample — filterable by client name (a field stored on each case).
- **Lean view** (toggle, off by default): a condensed per-case listing showing status, start date, day count (days elapsed since start, derived), and expected timeline date. Aimed mainly at a client-side "team leader" contact who wants a quick overview, but reachable by anyone via the toggle — no separate access tier enforced.
- **Shadow cases toggle** (nested inside lean view only, off by default): reveals shadow cases (see below) alongside real cases. Also not access-gated — just an extra step to find.
- After a case closes, it drops out of this view entirely for the client; only a pending review request surfaces separately (see Reviews).

## Shadow cases
- Represents a case that's expected to start soon but hasn't formally opened yet — a heads-up placeholder, not a full case.
- No case number. May carry an internal-only identifier not shown to any user.
- Holds mostly free notes; rarely needs more structure than that.
- Visible to the lab's team leader, and to clients only via the lean-view shadow toggle (see above).
- Later "evolves into" a real case once it's ready to formally open — exact mechanics (same record promoted into a Case vs. a new Case created separately and the shadow entry cleared) still open, see Open Questions.

## Versioning
- Format: **MAJOR.MINOR.PATCH**, starting at `0.1.0`.
- **Patch** bumps for a fix to something already launched (e.g. `0.2.0` → `0.2.1`).
- **Minor** bumps once a feature is considered done and launched for real use; patch resets to 0 (e.g. `0.1.3` → `0.2.0`).
- **Major** has no concrete trigger yet beyond the semver default: `1.0.0` marks the app going into real day-to-day use for actual cases (replacing whatever's used today); later majors would mark something similarly big (a major re-architecture, a new module) — to be decided when it comes up.
- **Testing suffix**: while a version is still being worked on and hasn't launched yet, it carries a `-tNN` suffix (two digits, zero-padded), e.g. `0.3.0-t01`, `0.3.0-t02`, `0.3.0-t03`... Once satisfied, it launches as the plain version with the suffix dropped (`0.3.0`). This applies the same way to a bug fix: `0.2.1-t01` for a quick check, then `0.2.1` once confident. The base number (minor vs. patch) says *what kind* of change it is; the `-tNN` suffix says *whether it's live yet*.
- Displayed at the **top** of the app (e.g. near the header/app name), not in a footer — makes it easy to confirm which build loaded during active testing.
- Doubles as the mechanism for the "update available, refresh?" pattern from the App Build Standards: the running app's version is compared against the deployed version, and a mismatch triggers the prompt rather than a silent reload. **Implemented in `0.1.0-t02`+**: polls its own `index.html` on load and on tab-visibility-regained, regex-matches the `APP_VERSION` constant, shows a dismissible banner with a Reload button on mismatch (no interval polling — see Decisions Log).

## Environments (testing vs. launched)
The owner wants to keep working on a testing build while colleagues/clients continue seeing the last launched version, rather than everyone seeing every in-progress change immediately.
- **Two live URLs from the same repo, no branches or build step needed**: the launched app lives at `docs/` (the repo's GitHub Pages source folder, effectively the site root — see `CLAUDE.md`'s "Repo layout"; what colleagues/clients use); the working/testing build lives in a `docs/test/` subfolder, served by the same GitHub Pages deployment. "Launching" a tested version means copying `docs/test/`'s files up to `docs/` and dropping the `-tNN` suffix from the version string.
- **Data separation, same Firebase project**: originally planned as Firestore's **multiple databases** feature (a second named database, e.g. `test`, alongside `(default)`) rather than a naming convention, to avoid the risk of a missed prefix silently writing test data into production. **Revised 2026-09-17**: that feature needs the paid Blaze plan; on Spark (free, what this project is on) only `(default)` exists. Interim approach is a collection-name prefix instead — `docs/`'s round-trip test writes `ping`, `docs/test/`'s writes `test_ping` — accepting the original risk for now. Auth stays shared across both either way (only the data separation approach changed). Revisit real database-level isolation if the project ever moves to Blaze.
  - Build notes (superseded by the 2026-09-17 revision above, kept for if/when this project moves to Blaze): a named database would be created via the `gcloud` CLI (`gcloud firestore databases create --database=test --location=... --type=firestore-native`) or possibly the Firebase Console directly. Security Rules are deployed **per database**, so both databases would need their rules deployed separately. The Web SDK connects to a specific database via `getFirestore(app, "test")` instead of the plain `getFirestore(app)` for default.
- **Not separately installable**: `docs/test/` has no manifest/service-worker of its own — Android can't offer two independent home-screen install icons when one URL path is nested under the other (manifest `scope` is a strict prefix match with no way to exclude a subpath; confirmed after trying an explicit `id` field and a clean uninstall/reinstall, still collided). `/test/` is accessed via browser bookmark/tab instead. The real fix would be a second repo at a sibling (non-nested) path, not attempted since it costs a second repo to keep in sync — revisit only if separate installability starts to matter.
- **Status**: built in iteration 2, both pieces user-verified (root launched at `0.1.0`; `docs/test/`'s writes confirmed landing in `test_ping`, distinct from root's `ping`).

## Report
- The official report is authored outside this app (closed network). This app's job is to produce a **report section as a docx file**, structured so it can be inserted into that report via the closed network's existing docx-import path. Exact content/structure of that section — TBD.

## Reviews
- Triggered when a case reaches `closed`.
- Client can: decline (removes the request entirely), review later (dismisses the prompt but keeps the link available), or complete it.
- A completed review has several 1-5 ranking questions plus a free-text area (exact question set TBD).
- Reviews are stored independently of the case record, so they survive the case's eventual deletion at `archived`.
- Admin may need elevated access here for anonymity reasons — deferred.

## Phase plan
1. **Infrastructure — built, launched at plain `0.1.0`, live at `https://matanyaa.github.io/smart-lab/`.** Login (username + synthetic-email Firebase Auth), Firestore round-trip, version display, manifest + service worker (home-screen install), and the update-check banner are all working, confirmed on desktop and phone.
2. **Environments (testing vs. launched) — built, `docs/test/` at `0.2.0-t01`, live at `https://matanyaa.github.io/smart-lab/test/`.** Data separated via a collection-name prefix (not the originally-planned second Firestore database — that needs the paid Blaze plan). Not separately installable as its own home-screen app (a web-platform limitation); accessed via browser bookmark/tab.
3. **Login types & Admin (roles, verifier tag, password reissue) — next iteration.** Username-keyed identity model (`users/{uid}` + `usernames/{username}` lookup, so a `uid` can be swapped out without disturbing anything referencing the person by username); an admin-only screen to add users, edit role/tag/status, and reissue a password; login as each type to confirm it reads back correctly. Delete-user deliberately out of scope — see Authentication section.
4. **Core data model:** case/sample/action/stage structures, workflow catalog, role-based access, once remaining open questions above are resolved enough to build against.
5. **Client visibility:** per-sample stage-only view for clients, once the access model is chosen.
6. **Reviews:** post-closure review flow.
7. **Reporting:** docx section generation per case.

Given that, decided to stay on Spark and defer delete-user/change-password entirely for now rather than build a partial manual-Console workaround. Also settled a role-model simplification for this iteration: the stored `role` field collapses Case manager + Operator into a single `worker` value (both are "TBD/could split later"), and Verifier becomes a boolean tag rather than a fifth role value, combinable with `team_leader`/`worker` but not `client`. Next iteration scoped as Phase plan item 3.
- 2026-09-17 — Custom-auth question resolved: considered dropping Firebase Auth entirely for full control over user management, rejected — Firestore security rules have no other way to trust a caller's identity, so ditching Firebase Auth would mean giving up essentially all real data-access enforcement (rules trust `request.auth`, which needs a real auth provider behind it). Instead settled on keeping Firebase Auth but redesigning around ever needing the Admin SDK for another user's account: usernames become the stable identity (what future case/action data will reference), decoupled from the underlying Firebase `uid` via a small `usernames/{username} → authEmail` lookup doc. This makes "reissue" possible — admin creates a fresh Firebase account and repoints the username's lookup at it — as a Spark-compatible, no-Blaze substitute for a true admin-forced password reset; a person keeps their username, role, verifier tag, and any future by-username assignments completely undisturbed across a reissue, only the password (and an invisible internal email) changes. Also concluded that a genuine Auth-account delete may never actually be needed at all now that disable (permanent, free) and reissue (this) cover the two real cases — kept as a manual Firebase Console fallback rather than an in-app feature, on the off chance it ever comes up. Updated TASK.md (rev 2) to build this model instead of the simpler uid-keyed draft from rev 1, before any of it got built.
- 2026-09-17 — Android install collision found: after installing the root app to a phone home screen, visiting `docs/test/` no longer offered a separate install — Chrome's install identity defaults to `start_url`, but scope is a path-prefix match, and root's scope (`/smart-lab/`) technically contains `/smart-lab/test/`, so the already-installed root app's record can swallow the nested test build instead of Chrome offering a fresh, distinct install. First attempt: added an explicit `"id"` field to both manifests (`/smart-lab/` and `/smart-lab/test/`), since `id` is the spec's mechanism for disambiguating app identity. **Confirmed not sufficient** — user did a clean uninstall of the existing icon and reinstalled fresh, still collided. `id` disambiguates identity for things like WebAPK updates, but doesn't override the browser's scope-based "this URL is already covered by an installed app" link-capturing logic, and there's no way to carve a subpath exclusion out of a manifest `scope` (it's a strict prefix match) — two independently-installable PWAs where one path is nested inside the other isn't achievable on the web platform, period. Considered: (a) move `docs/test/` to a separate sibling-path repo (genuinely fixes it, costs a second repo to keep in sync, contradicts the current "same repo" convention), (b) drop separate installability for `/test/`. User chose **(b)**: removed `docs/test/manifest.json` and `docs/test/sw.js` entirely (no install path offered at all now, cleaner than an install that silently fails), `docs/test/index.html`'s `<head>` no longer links a manifest, `<title>` changed to "Smart Lab (Test)" to at least distinguish it as a browser tab/bookmark. `/test/` is bookmark/tab access only going forward — revisit if a separate repo ever becomes worth the sync overhead. Also (unrelated to this fix but discovered along the way): considered and rejected a single installed app with a runtime test/launch toggle, or differentiating by login username, since neither solves the actual need — `docs/test/` exists to test different *code* before promotion, not just different data or a different account.
- 2026-09-17 — Iteration 3 built (`docs/test/`, `0.3.0-t01`): `users/{uid}` + `usernames/{username}` model, admin screen (add user, inline edit role/verifier/status), reissue. Real decisions made during the build, beyond what TASK.md rev 2 already specified:
  - **`setup/firestore.rules` rewritten from scratch**, not just extended — the old rule was a single blanket `match /{document=**} { allow read, write: if request.auth != null; }`. Firestore rules are permissive-OR across every matching `match` block for a given path, so leaving that blanket rule in place *alongside* new admin-gated rules for `users`/`usernames` would have silently let any signed-in user bypass the admin gate entirely (the blanket rule would still match and allow it). Replaced with explicit per-collection rules instead: `usernames/{username}` (public read via `allow read: if true`, admin-only write), `users/{uid}` (self-or-admin read, admin-only create/update, delete always denied), and narrow `ping`/`test_ping` rules preserving the old any-signed-in-user behavior for those two iteration-1 collections specifically. `isAdmin()` is a rules function doing `get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin'`.
  - **Reissue email disambiguation scheme**: `${username}.r${Date.now()}@smart-lab.internal` — timestamp suffix guarantees uniqueness without needing to track a counter anywhere, and the `.r<big number>` pattern is obviously not a normal username if ever seen directly in the Firebase Console.
  - **Secondary-app-instance pattern**: `initializeApp(firebaseConfig, `secondary-${Date.now()}`)` (named uniquely per call, so concurrent add-user/reissue actions can't collide on app-instance identity) → `createUserWithEmailAndPassword` on that instance's own `getAuth()` → sign out and `deleteApp()` the secondary instance in a `finally` block, before ever touching Firestore from the primary (still-admin) session. Used identically for both add-user and reissue.
  - **Admin-bootstrap instructions** written into `setup/README.md`'s new section — the one subtlety worth flagging: the `users/{uid}` document ID must be the actual Firebase Auth UID (copied from the Authentication tab), not auto-generated, while `usernames/{username}`'s document ID is the username itself, not a UID. Easy to transpose by accident since both are manual Console entries side by side.
  - Root (`docs/index.html`) untouched, as scoped — still logs in via the old fixed-formula email, unaffected by any of this.
